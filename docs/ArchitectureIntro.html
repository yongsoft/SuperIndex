1. The one-sentence version

Two indexing engines that produce the same tree, plus one agentic retrieval loop. Everything else is supporting machinery.

The consequence of that design is the cleanest thing about the codebase: the retrieval side does not care how a document was indexed. Swap the indexing engine and no retrieval code changes.

This project already leans on that property. Adding the Azure Document Intelligence extractor changed only where the text comes from; the tree builder and the retrieval loop were untouched.

What is deliberately absent

There is no vector store and no embedding model anywhere in the dependency list. Not even numpy. Retrieval is the chat model reasoning over an explicit tree, which is what makes an answer traceable to a page number rather than to a cosine score.

2. Layered architecture

Five layers, but only two of them hold real logic. The rest are adapters and storage.

3. Two indexing paths

The two engines have very different cost profiles, and the choice is per document.

Why the offline path matters

Because the flash skeleton needs no LLM, the entire corpus can be parsed and its structure inspected before spending anything. In this project that is what makes the 10-document corpus cheap to work with: the skeleton build takes about 45 seconds and costs nothing.

The classic path is more accurate on documents that have a real table of contents, but note what the author put next to it — check_if_toc_extraction_is_complete, check_if_toc_transformation_is_complete, _validate_physical_indices. Those functions exist because the LLM step is not reliable and has to be verified.

4. The retrieval loop

At query time the chat model is not given a ranked list of chunks. It is given tools and a tree, and it decides what to look at.

The tool surface is tiny

_READ_TOOLS = ("browse_documents", "get_document",
               "get_document_structure", "get_page_content")
_MANAGEMENT_TOOLS = ("remove_document",)
ToolPurposeNote
browse_documentsList documents and foldersEntry point for multi-document corpora
get_documentDocument metadataStatus, page count, description
get_document_structureReturn the treePaginates when the tree exceeds a budget
get_page_contentFetch page textAccepts a page spec like "1-3,5"
remove_documentDelete a documentNot exposed by default
Why get_document_structure paginates. It splits oversized trees via _split_structure and _split_oversized_node. On the AIA corpus this is observable: a 452,593-character tree comes back as 9 parts. This is intentional, not a defect — but it is also the main driver of retrieval cost, because every part is a round trip.

Defensive details

Two small things in agent_tools.py say a lot about running this in production:

  • _coerce_bool_args — the docstring reads: "Models routinely send booleans as JSON strings ("false"); the bare truthiness tests downstream would read those as True."
  • Response envelopes carry a next_steps field, so each tool result tells the model what it could usefully do next rather than leaving it to guess.

6. Storage and the node model

The tree and the page text are stored separately. The tree is small and can be held in memory; the text is large and fetched on demand.

This split is worth copying. This project's own navigator uses the same shape — a small always-loaded manifest.json for routing, and large per-document trees fetched by key.

7. Implementation details worth knowing

Configuration lives in pageindex/config.yaml

toc_check_page_num: 20          # how many leading pages to scan for a TOC
max_page_num_each_node: 10      # cap on pages per node
max_token_num_each_node: 20000
if_add_node_id: "yes"
if_add_node_summary: "yes"
if_add_doc_description: "no"
if_add_node_text: "no"          # <-- why the tree has no body text by default

That last line is the single most common surprise. With if_add_node_text: "no" the body text is stripped after summaries are generated, so the tree carries titles and summaries but nothing you can quote. Retrieval has to go back to pages.json — which is by design, but it means a caller who only reads the tree will find no content in it.

Five things that will cost you an afternoon

#IssueWhat to do
1 md_to_tree() has a real bug: summary_token_threshold defaults to None, and get_node_summary() compares num_tokens < summary_token_threshold — a TypeError. Pass it explicitly. The CLI defaults to 200. The Markdown path is simply less tested than the PDF path.
2 The local client accepts PDF only (local_api.py rejects anything else), so Markdown cannot enter the normal retrieval path. Either pre-convert to PDF, or build your own layer — which is what nav/ in this project does.
3 PDF parsing uses ProcessPoolExecutor(mp_context=spawn). The calling script must be a real file with an if __name__ == "__main__": guard. Running via heredoc hangs with no network traffic — check lsof -nP -iTCP to confirm it is stuck in spawn rather than waiting on an API.
4 Node summaries average ~1,167 characters and dominate the tree — 89% of its size on the AIA corpus. Shorten summaries before blaming retrieval cost. Cutting them to ~300 characters took the same tree from ~113K tokens to ~35K, and from 9 pagination parts to 1–2.
5 litellm.success_callback does not fire on the openai-agents path. To measure token usage you must wrap litellm.acompletion directly.

Where the time actually goes

Local I/O is not the bottleneck. Measured on this corpus: tree.json read and parse 0.8 ms, pages.json 1.8 ms, get_page_content for three pages 3 ms. Everything else is LLM round trips — which is why the levers that matter are reasoning effort, summary length, and the number of pagination parts.

8. How this project extends it

This repository builds on upstream without editing a single file inside PageIndex/. Two extension points are used.

Extraction backend — extractors/

Upstream reads the PDF text layer with PyPDF2. That is free but has two hard limits on financial reports: tables come out mangled, and image-only PDFs are refused outright.

extractors/backend.py resolves which extractor to use and, when Azure Document Intelligence is configured, takes over LocalAPI._extract_page_texts by monkeypatching. The method is a staticmethod returning one string per page, so a drop-in replacement is enough and upstream stays pristine.

The extraction backend never switches silently. Every entry point prints which one it used and why. And when Azure is configured but a call fails, the run aborts rather than degrading to the text layer — a broken key would otherwise quietly change index quality.

Corpus navigation — nav/

Upstream's tree models one document. nav/ adds a level above it for corpora with deep directory structures and thousands of files:

question
 ├─ level 1: walk the directory tree to pick candidate files
 └─ level 2: walk each candidate's chapter tree to pick sections
        ↓
      section text + provenance

Both levels use the same principle as upstream: the model chooses, no similarity ranking. Where the corpus is large, the directory tree is still small enough to read whole, which keeps level 1 to two calls regardless of depth.

What stayed the same

Because both indexing engines emit the same tree, none of this required touching the tree builder or the retrieval loop. The extensions changed where text comes from and how many documents are addressed — not how a tree is shaped or traversed.
