1. The one-sentence version

Two indexing engines that produce the same tree, plus one agentic retrieval loop. Everything else is supporting machinery.

The consequence of that design is the cleanest thing about the codebase: the retrieval side does not care how a document was indexed. Swap the indexing engine and no retrieval code changes.

This project already leans on that property. Adding the Azure Document Intelligence extractor changed only where the text comes from; the tree builder and the retrieval loop were untouched.

What is deliberately absent

There is no vector store and no embedding model anywhere in the dependency list. Not even numpy. Retrieval is the chat model reasoning over an explicit tree, which is what makes an answer traceable to a page number rather than to a cosine score.

2. Layered architecture

Five layers, but only two of them hold real logic. The rest are adapters and storage.

3. Two indexing paths

The two engines have very different cost profiles, and the choice is per document.

Why the offline path matters

Because the flash skeleton needs no LLM, the entire corpus can be parsed and its structure inspected before spending anything. In this project that is what makes the 10-document corpus cheap to work with: the skeleton build takes about 45 seconds and costs nothing.

The classic path is more accurate on documents that have a real table of contents, but note what the author put next to it — check_if_toc_extraction_is_complete, check_if_toc_transformation_is_complete, _validate_physical_indices. Those functions exist because the LLM step is not reliable and has to be verified.

4. The retrieval loop

At query time the chat model is not given a ranked list of chunks. It is given tools and a tree, and it decides what to look at.

The tool surface is tiny

_READ_TOOLS = ("browse_documents", "get_document",
               "get_document_structure", "get_page_content")
_MANAGEMENT_TOOLS = ("remove_document",)
ToolPurposeNote
browse_documentsList documents and foldersEntry point for multi-document corpora
get_documentDocument metadataStatus, page count, description
get_document_structureReturn the treePaginates when the tree exceeds a budget
get_page_contentFetch page textAccepts a page spec like "1-3,5"
remove_documentDelete a documentNot exposed by default
Why get_document_structure paginates. It splits oversized trees via _split_structure and _split_oversized_node. On the AIA corpus this is observable: a 452,593-character tree comes back as 9 parts. This is intentional, not a defect — but it is also the main driver of retrieval cost, because every part is a round trip.

Defensive details

Two small things in agent_tools.py say a lot about running this in production:

  • _coerce_bool_args — the docstring reads: "Models routinely send booleans as JSON strings ("false"); the bare truthiness tests downstream would read those as True."
  • Response envelopes carry a next_steps field, so each tool result tells the model what it could usefully do next rather than leaving it to guess.

6. Storage and the node model

The tree and the page text are stored separately. The tree is small and can be held in memory; the text is large and fetched on demand.

This split is worth copying. This project's own navigator uses the same shape — a small always-loaded manifest.json for routing, and large per-document trees fetched by key.

7. Implementation details worth knowing

Configuration lives in pageindex/config.yaml

toc_check_page_num: 20          # how many leading pages to scan for a TOC
max_page_num_each_node: 10      # cap on pages per node
max_token_num_each_node: 20000
if_add_node_id: "yes"
if_add_node_summary: "yes"
if_add_doc_description: "no"
if_add_node_text: "no"          # <-- why the tree has no body text by default

That last line is the single most common surprise. With if_add_node_text: "no" the body text is stripped after summaries are generated, so the tree carries titles and summaries but nothing you can quote. Retrieval has to go back to pages.json — which is by design, but it means a caller who only reads the tree will find no content in it.

Five things that will cost you an afternoon

#IssueWhat to do
1 md_to_tree() has a real bug: summary_token_threshold defaults to None, and get_node_summary() compares num_tokens < summary_token_threshold — a TypeError. Pass it explicitly. The CLI defaults to 200. The Markdown path is simply less tested than the PDF path.
2 The local client accepts PDF only (local_api.py rejects anything else), so Markdown cannot enter the normal retrieval path. Either pre-convert to PDF, or build your own layer — which is what nav/ in this project does.
3 PDF parsing uses ProcessPoolExecutor(mp_context=spawn). The calling script must be a real file with an if __name__ == "__main__": guard. Running via heredoc hangs with no network traffic — check lsof -nP -iTCP to confirm it is stuck in spawn rather than waiting on an API.
4 Node summaries average ~1,167 characters and dominate the tree — 89% of its size on the AIA corpus. Shorten summaries before blaming retrieval cost. Cutting them to ~300 characters took the same tree from ~113K tokens to ~35K, and from 9 pagination parts to 1–2.
5 litellm.success_callback does not fire on the openai-agents path. To measure token usage you must wrap litellm.acompletion directly.

Where the time actually goes

Local I/O is not the bottleneck. Measured on this corpus: tree.json read and parse 0.8 ms, pages.json 1.8 ms, get_page_content for three pages 3 ms. Everything else is LLM round trips — which is why the levers that matter are reasoning effort, summary length, and the number of pagination parts.

Part II — SuperIndex

8. Why a layer above PageIndex was needed

PageIndex's tree models one document. That is the right unit for the question it was designed to answer — "where in this report is the figure?" — and it answers it well.

But the real corpus is not one report. It is thousands of files spread across a directory tree several levels deep, and the first question a user asks is not "where in this report" but "which report?". PageIndex's browse_documents tool lists documents, but listing is not navigating: hand a model 1,000 file names in one flat list and it is guessing.

PageIndex aloneThe problem at corpus scale
Unit of addressing One document, addressed by page range Need to pick which document before any page range is meaningful
Document discovery browse_documents returns a flat list A flat list of 1,000 names does not fit a prompt, and gives no basis for choosing
Directory structure Not modelled — folders are a cloud-side grouping The directory tree is the strongest routing signal available (year, entity, report type)
Extraction PDF text layer via PyPDF2 Mangles tables; refuses scanned PDFs
SuperIndex adds one level above PageIndex and one layer underneath it. Above: a corpus tree so the model can narrow from thousands of files down to a handful. Underneath: a pluggable extraction backend so the text going into the tree is worth indexing.

9. How SuperIndex composes with PageIndex

SuperIndex is a layer, not a fork. Not a single file inside PageIndex/ is modified — everything is either a wrapper or a monkeypatch applied at runtime.

The two extension points, and why they are shaped that way

ExtensionMechanismWhy not edit upstream
Extraction backend
extractors/backend.py		 Monkeypatches LocalAPI._extract_page_texts. That method is a staticmethod returning one string per page, so a drop-in replacement is sufficient. Upstream stays git pull-able, and the diff against it stays empty. Two runtime knobs (SUMMARY_CONCURRENCY, reasoning_effort) are applied the same way.
Corpus navigator
nav/		 Sits entirely beside upstream. It builds its own index and never calls into PageIndex/ for retrieval. The navigator answers a different question (which file?) than upstream does (where in the file?). Keeping them separate means either can be replaced alone.

The reason both are possible is the property noted in Part I: the indexing engines emit the same tree shape, so nothing downstream depends on how a tree was built. SuperIndex changes where text comes from and how many documents are addressed — not how a tree is shaped or traversed.

10. Three-level addressing and the index split

SuperIndex addresses a corpus at three levels. Each level has its own index file, sized so that the cheap level stays resident and the expensive one is fetched only when needed.

Measured on a 144-file / 229-directory corpus

QuantityValueWhy it matters
Structural index build (no LLM)0.09 sYou can index a corpus before deciding whether it is worth summarising
manifest.json125 KBSmall enough to hold in memory and re-read per query
Full directory tree listing8,904 characters≈2K tokens — fits one prompt, which is what makes level 1 cheap
Chapter nodes2,304Spread across per-document files, so never all loaded at once
The load-bearing observation: the directory tree is far smaller than the file count. 144 files live in 229 directories — and directories are what level 1 reads. That is why level 1 can show the whole tree in a single call, and why its cost does not grow with directory depth.

This mirrors upstream's own split (tree.json small and resident, pages.json large and on demand), extended one level up.

11. The two-level navigator

Retrieval walks the two levels in sequence. Every step is a model decision — there is no similarity ranking anywhere in it.

Why level 0 shows the entire tree instead of descending

The first implementation descended one directory level at a time. It was slower and less reliable, for a reason worth recording:

Level-by-level descentWhole tree in one call
LLM callsOne per level, so it grows with depthTwo, regardless of depth
Model contextSees one level at a time — cannot compare across branchesSees the whole shape, including which branch is deeper
Failure modeAn early wrong turn is unrecoverableA wrong branch is still visible in context

Descent is still implemented and used as a fallback when the directory count exceeds a budget (240 by default) — but it is the exception, not the default path.

The extraction backend underneath

Level 0 answers which file. The extraction backend answers what text goes into the tree in the first place — and it matters more than it sounds, because a tree built from mangled text is wrong no matter how good the navigation is.

Text layer (default fallback)Azure Document Intelligence
Costfreeper page
Tablesmangled — a chart page flattens to 175230, two numbers fused, label-to-value association gonereal Markdown tables
Scanned / image-only PDFsrefused outrightOCR'd
Page anchorssynthesised as <!-- page: N -->injected at real page boundaries, read from analyzeResult.pages[].spans[].offset
Configured means default. Set AZURE_DI_ENDPOINT and AZURE_DI_KEY in .env and every entry point takes it up automatically — no flag to remember. With nothing configured you get the text layer, exactly as before. The backend never switches silently: each run prints which one it used and why.
A configured-but-failing backend aborts the run. Degrading quietly to the text layer would hide a wrong key or endpoint and change index quality without anyone noticing. AZURE_DI_FALLBACK=1 opts into the soft behaviour.

12. Design decisions that are load-bearing

These were each arrived at by getting them wrong first. They are recorded here so they are not "tidied up" later.

DecisionWhy
Prompts say "select at least one", never "leave blank if nothing is relevant". The first version offered an escape hatch. The model took it unpredictably — the same question would navigate correctly on one run and abort on the next. Models default to caution; do not give them a reason to abstain. Relevance is better judged downstream.
Year is the highest-weighted routing signal. Cross-period confusion is the dominant error in financial QA. Years appear in directory paths, so extracting them from the question serves double duty: a hint in the prompt and a scoring term in the fallback.
Fallbacks resolve at the current level, not globally. Falling back to the whole corpus is a blunt instrument that gets worse as the corpus grows. If the model abstains at a level that already has candidate files, use those files — not all 144.
The manifest and the trees are separate files. Routing must stay cheap. Keeping chapter trees out of the always-loaded file is what lets manifest.json stay at 125 KB for a corpus of 144 files.
Extraction failures are loud. Silent degradation changes index quality without changing any observable behaviour — the worst kind of bug in a retrieval system.
Nothing inside PageIndex/ is edited. Keeps upstream git pull-able and the diff empty. All three runtime customisations (_extract_page_texts, SUMMARY_CONCURRENCY, reasoning_effort) are applied from outside.

13. What SuperIndex does not solve

Worth being explicit about, because these are the questions a new owner will hit.

LimitDetail
Locating is not the same as computing. The navigator finds the right section. If the answer requires arithmetic across sections, the model still does it by reading text. Numbers ultimately need a structured path — see docs/dify-improvement-plan.md for the proposal.
Chapter summaries need an LLM. A one-time cost per corpus. Without them, section selection degrades to token matching.
PDFs depend on bookmarks or Azure DI. With neither, a PDF falls back to one node per page — coarse but navigable. It is never silently dropped.
Directory quality sets the ceiling. If a corpus is thousands of files flattened into one directory, level 0 degrades to listing thousands of names. That is a corpus-organisation problem, not a navigator one.
Fallbacks match tokens, not synonyms. Asking about "life insurance" will not match a directory named "人身险". Swapping in an embedding pre-filter would fix it — at the cost of reintroducing the similarity problem the whole design avoids.
Validated on synthetic corpora, not production ones. 16-file and 144-file corpora with a known structure. The scale numbers above are real; the routing accuracy on a messy real corpus is not yet measured.
The honest summary. SuperIndex makes the which file, which section problem cheap and traceable at corpus scale. It does not make numeric answers exact, and it has not been tested against a genuinely messy production corpus. Both are known and recorded rather than papered over.
